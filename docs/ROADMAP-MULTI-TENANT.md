## 1. Objetivo e modelo

Migrar o Empire do modelo atual **"1 instância = 1 empresa"** (isolamento físico perfeito, mas caro de operar) para um **modelo híbrido**:

- **Agency multi-tenant** (uma instância com N sub-contas isoladas por dentro, espelhando o GHL) para a maioria dos clientes.
- **Instância isolada** (modelo atual) mantida como tier "enterprise"/alto risco.

A parte mais crítica e arriscada é o **isolamento de credenciais** (Fase 2): hoje todas as chaves (GHL, Meta, OpenRouter, webhooks) são globais por instância, lidas como env var em 16+ edge functions. Sem isso, a proteção entre clientes depende 100% do RLS.

### 7.4 Arquitetura que a próxima IA não pode violar

1. **Modelo:** uma agência contém subcontas (`agency_workspaces`) e cada subconta é um `workspace`. Dados de negócio usam `workspace_id`; RLS filtra por workspace e libera owner/admin de agência somente via `can_access_workspace_via_agency`.
2. **Single-Tenant Lock:** o dashboard comum continua sem seletor/terminologia de workspace. A área `/agency/*` é operacional para o dono da agência; não transformar o produto em UI multi-workspace sem decisão explícita.
3. **Credenciais:** GHL e Meta são resolvidos por subconta no Vault, via `workspace_integration_credentials`; o fallback “workspace mais antigo” foi removido. Sem credencial, a função falha fechada e nunca reutiliza token de outro cliente.
4. **Meta Ads:** cada subconta possui integração Meta própria. A migration `20260823000000` e `sync-meta-ads-backfill` propagam `workspace_id`; `meta_ads_account_daily` recebeu isolamento/RLS de agência. `docs/HANDOFF-MULTI-TENANT-META-ADS-ACCOUNT-DAILY.md` confirma que os gaps históricos 1/2 foram resolvidos pela PR #47 e pelas migrations promovidas.
5. **Privilégios:** cron e funções administrativas exigem `service_role` por guard fail-closed. Credencial nunca pode retornar ao cliente; `SUPABASE_SERVICE_ROLE_KEY` nunca entra no frontend.
6. **IA:** `bot-chat` e `prevendas-ai` continuam obrigatoriamente em `qwen/qwen3.6-plus` via OpenRouter; não trocar para OpenAI, Anthropic ou Claude.

## 8. PLANEJADO (futuro, não iniciado) — Inscrições no Formulário: leitura de Supabase externo por sub-conta

> **Status:** ⬜ não iniciado — só registro de arquitetura para execução futura. Nenhuma migration, edge function, RPC ou componente React foi criada a partir deste item. Não depende de nenhuma fase em andamento; pode ser puxado a qualquer momento depois que uma sub-conta real existir.

### 8.1 Origem e problema

Hoje existe um app externo (Vercel, fora do `eb-dash2`) que recebe submissões de formulário personalizado e insere leads na tabela `"aplic-acelerador"` deste projeto Supabase (o de produção, `qzesffnkqgelmtfblzkr`), usando a **service role key** diretamente numa função serverless (ver skill `/ghl-form-integration` — padrão "queue-first": grava no Supabase primeiro, depois faz upsert de contato+tags no GHL, com retry por cron em caso de falha). A tabela tem RLS habilitado mas **zero policies** (só a service role lê/escreve) e **não tem `workspace_id`**. Não existe nenhuma tela no `eb-dash2` que exiba esses dados — o dono pediu uma aba nova, "Inscrições no Formulário", para ver esses leads dentro do dashboard.

A pergunta que motivou este item: como estender esse recurso para outras sub-contas (agência multi-tenant), sem (a) tornar `aplic-acelerador` multi-tenant e (b) sem distribuir a `SUPABASE_SERVICE_ROLE_KEY` deste projeto para clientes de sub-conta (violaria a regra 17 do `CLAUDE.md`/AGENTS — segredo nunca sai do backend).

### 8.2 Decisão do dono (revista e confirmada nesta sessão, 2026-07-14)

**A tabela `"aplic-acelerador"` NÃO será multi-tenant.** Ela continua existindo exatamente como hoje — RLS habilitado sem policies, só acessível via service role, **exclusiva da sub-conta default** (a instância atual/workspace único). Ela **não** ganha coluna `workspace_id`, não é retrofitada na Fase 6, não entra na suite de isolamento cross-tenant.

**Para qualquer outra sub-conta que quiser o mesmo recurso, o modelo é replicação + conexão externa, não multi-tenant compartilhado:**

1. A sub-conta precisa criar **sua própria infraestrutura** — um projeto Supabase próprio e um projeto Vercel próprio, replicando exatamente o mesmo padrão hoje descrito na skill `/ghl-form-integration` (formulário → tabela própria → GHL da própria sub-conta, com o mesmo padrão queue-first + retry).
2. Depois, a sub-conta **conecta essa tabela externa ao nosso sistema, só para leitura** — nunca escrita. O módulo novo (dentro do app de leads/`eb-dash2`) não guarda nenhum lead; ele apenas busca e exibe dados de um Supabase de terceiro (o da própria sub-conta), sob demanda.
3. **Tipo de chave aceito, decisão do dono:** a sub-conta fornece a **service role key do próprio projeto Supabase dela** (não uma anon key + RLS configurada por ela). Justificativa: é o banco dela — o risco de uma chave forte concentrado ali é só dela — e evita depender de ela configurar RLS corretamente do próprio lado, o que teria mais chance de sair errado (aberto demais ou quebrado). Essa chave é armazenada no **nosso** Vault (nunca em texto puro, nunca exposta ao navegador), exatamente como já fazemos com as credenciais BYOK de GHL/Meta em `workspace_integration_credentials` (Fase 2).

### 8.3 Desenho técnico recomendado (para quando for executado)

1. **Sub-conta default (a atual):** nenhuma mudança de infraestrutura — o módulo lê diretamente da tabela local `"aplic-acelerador"` deste mesmo projeto. Falta decidir, na execução, como a leitura chega à UI sem dar acesso amplo à tabela: (a) uma policy RLS de SELECT restrita a owner/admin do workspace default, ou (b) uma edge function autenticada que lê com service role e valida que o usuário pertence ao workspace default (mais alinhado ao padrão já usado em tabelas sensíveis do projeto, ex. `webhook-ghl`/`ghl-api-worker`).

2. **Outras sub-contas — nova tabela `workspace_external_form_sources`** (nome de trabalho), no mesmo molde já usado em `workspace_integration_credentials` (Fase 2) e `outbound_webhooks` (Fase 2 Fatia 7): credencial num Vault, nunca em texto puro; gravação só via RPC `SECURITY DEFINER` admin-only (ex.: `save_workspace_external_form_source`, espelhando `save_workspace_credential`); leitura de status (configurado/não configurado, testado/não testado) via RPC que **nunca** devolve o segredo (espelhando `get_workspace_credential_status`).
   - Campos previstos: `workspace_id`, `provider` (fixo `'supabase'` por ora), `external_project_url`, `secret_key_id` (a service role key da sub-conta, no Vault), `external_table_name` (permite a sub-conta nomear a tabela diferente de `aplic-acelerador` — decisão de nome fixo vs configurável ainda em aberto para a execução), `status` (`not_configured` / `testing` / `connected` / `error`), `last_tested_at`, `last_error`.

3. **Edge function de leitura (proxy) — nunca expor a chave externa no navegador.** Um endpoint autenticado (JWT do usuário + checagem de papel no workspace, mesmo padrão de `resolve-workspace-credentials.ts`) resolve a credencial do Vault e faz a chamada PostgREST no projeto Supabase **da sub-conta**, devolvendo os dados já formatados para o frontend. A chave externa nunca chega ao bundle do cliente — mesma razão pela qual a service role nunca vai para `VITE_*` (regra 17 do `CLAUDE.md`).

4. **Gate de abertura do módulo — regra explícita do dono.** A aba "Inscrições no Formulário" só pode renderizar conteúdo se `status = 'connected'` para o workspace atual:
   - Sub-conta default → sempre "conectado" (usa a tabela local, não passa pelo fluxo de fonte externa).
   - Outras sub-contas sem fonte configurada → o módulo **nem abre** — mostrar estado vazio com instruções de configuração em vez de tentar renderizar uma tabela vazia ou dar erro.
   - Um botão "Testar conexão" (mesmo padrão de `test-workspace-credential`, Fase 4) valida URL + chave antes de marcar `status = 'connected'`.

5. **Frontend — decisão do dono:** nova aba dentro de `eb-dash2/src/pages/workspace/WorkspaceGhlConfigPage.tsx`, ao lado de "Assistente IA"/"Mapeamento avançado" (estender o union `activeTab`, novo `TabsTrigger` + `TabsContent`). Hook novo para chamar a edge function de leitura, com paginação (a regra de limite de 1000 rows do PostgREST — ver seção "LIMITE CRÍTICO" do `CLAUDE.md` — vale também para a REST API externa da sub-conta).

6. **Documentação obrigatória quando for executado** (gates da skill `omnx-code`): `docs/ARQUITETURA.md`, `docs/TABELAS-SISTEMA.md` (nova tabela `workspace_external_form_sources` + registrar explicitamente que `aplic-acelerador` é single-tenant-only, por decisão de produto, não por dívida técnica), um doc próprio (ex. `docs/INSCRICOES-FORMULARIO-EXTERNO.md`), `docs/NIVEIS-DE-ACESSO.md` (gate 1.6b — quem pode configurar/ver a fonte externa: provavelmente só owner/admin do workspace), `docs/UML.md` (gate 1.6c — nova entidade `workspace_external_form_sources` e o fluxo de leitura via proxy).

### 8.4 Pontos em aberto para a execução

- Nome fixo (`aplic-acelerador`) vs configurável (`external_table_name`) da tabela remota na sub-conta.
- Se a leitura da sub-conta default passa por RLS direta ou por edge function proxy (ambas cumprem a regra de segurança; falta decidir qual é mais simples de manter).
- Se o retry de falha no GHL continua no cron Vercel de cada sub-conta (modelo replicado, cada uma cuida da própria infra) — este item não muda essa parte, já que a tabela remota é inteiramente da sub-conta.
