# Marcel Marcondes — Rodada 2

Vou reagir a dois membros com quem tenho divergências reais aqui.

**Para Hormozi:** Alex, você disse que "design amador é problema de clareza de propósito" e concordo com o diagnóstico — mas discordo do remédio implícito, que é "tire tudo e mostre só o número". Isso funciona pra quem usa o produto uma vez por dia com uma pergunta só. O gestor de marketing que usa esse dashboard tem três perguntas simultâneas: onde estão os leads hoje, qual campanha está performando, e o que o SDR está fazendo com o que chegou. São três contextos diferentes numa mesma ferramenta. O problema não é que o produto não tem clareza de propósito — é que ele tem três propósitos legítimos e ninguém definiu uma hierarquia entre eles por tela. Isso é diferente. O que falta não é eliminar, é sequenciar. Qual é a pergunta que o usuário traz quando abre essa tela específica? A resposta muda conforme o módulo. É customer centricity aplicada à arquitetura de informação, não minimalismo por princípio.

**Para Gary:** Você tocou no ponto mais importante da discussão e passou por cima dele rápido demais: o produto foi construído em dois mundos que não conversam. Eu quero aprofundar isso porque é onde o risco estratégico real mora. Quando o filtro de campanhas Meta não funciona, o gestor não abandona o filtro — ele cria um processo paralelo. Abre o Ads Manager, exporta um CSV, compara com o dashboard no papel. E esse processo paralelo vira o processo oficial. Em seis meses você tem uma equipe que usa o dashboard pra ver SDR e usa o Ads Manager pra ver campanha, e alguém vai perguntar "pra que serve esse dashboard mesmo?" Não é só bug de UX — é um risco real de tornar o produto redundante na rotina de quem deveria depender dele. A solução de cruzar no backend é correta e não negociável. O que eu adicionaria: antes de fazer o cruzamento técnico, definir qual é o identificador único que conecta campanha Meta com lead no CRM — utm_campaign, ad_id, ou outro campo — e tratar essa regra de match como um ativo de governança de dados, não como um detalhe de implementação. Se essa regra mudar, todos os relatórios históricos mudam junto. Isso precisa de versionamento e documentação, não só de código.

Sobre os filtros com itens inativos: Russell e Sandro diagnosticaram certo — é ausência de opinião do produto. Mas quero adicionar um framework prático aqui. O filtro não deveria ser só "tem dado neste período?" — ele deveria ter dois estados distintos: itens ativos no período (com contagem visível) e itens sem dado (colapsados com opção de expandir). Isso preserva a possibilidade de o usuário buscar uma campanha específica que sabe que existiu, mas não polui o dropdown padrão. É a diferença entre esconder e hierarquizar. Esconder cria frustração quando o usuário precisa do item. Hierarquizar respeita o contexto e ainda dá a saída de emergência.

Sobre o bug de delete: concordo com todos que é sintoma de ausência de governança, mas o Grant exagerou no "roleta-russa". O risco real aqui não é catástrofe — é erosão de confiança gradual. Operação que falha silenciosamente ensina o usuário a não confiar no feedback do sistema inteiro. Se o botão de delete não confirma, ele começa a duvidar se o filtro está funcionando, se o dado foi salvo, se o relatório é real. A solução não é só confirmação + log — é um padrão sistêmico de feedback para toda operação de escrita. Toda ação que muda estado precisa ter: estado intermediário visível (loading), confirmação de sucesso explícita, e erro legível se falhar. Isso vale pra delete, mas vale igual pra salvar uma meta, editar um lead, ou mudar um filtro salvo. Não é feature — é o mínimo de respeito pelo usuário que está tomando decisão com base no que o produto diz que aconteceu.
