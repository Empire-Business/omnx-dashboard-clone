# Alex Hormozi — Rodada 2

**Russell, você acertou o diagnóstico mas errou o remédio.**

Você disse que o problema é hierarquia de informação, não efeito visual. Concordo 100%. Mas depois você apresentou um framework — "herói visual, dois elementos de suporte, um call-to-action" — como se fosse mágico. Não é. Esse framework funciona para landing page de oferta. Dashboard operacional é diferente. O gestor de marketing não abre o painel pra ser convencido de nada — ele abre pra tomar uma decisão específica em menos de 60 segundos. A pergunta certa não é "onde está o herói visual?" A pergunta certa é: "qual é a decisão mais frequente que esse usuário toma, e o dado que responde essa decisão está a zero cliques da abertura?" Se a resposta for não, você tem problema de arquitetura de informação, não de design. Você pode ter hierarquia perfeita e ainda ter o dado errado no topo.

**Gary, você disse que o produto foi construído para funcionar, não para ser sentido. Isso é verdade, mas incompleto.**

O problema com focar em "o que o gestor sente às 8h da manhã" é que você está vendendo experiência antes de ter utilidade. Este produto tem usuários internos com dados reais. Isso significa que a utilidade básica já existe — eles já usam. O próximo passo não é alma, é atrito zero. Aqui está o problema real com os filtros Meta: o gestor abre o painel, aplica o filtro de campanha, e os dados da Meta simplesmente não aparecem. Ele não sente nada — ele confunde. E confusão mata confiança muito mais rápido do que design feio. A sequência correta é: primeiro fecha o loop de dados (Meta + CRM cruzados no backend), segundo remove o ruído dos filtros, terceiro refina a hierarquia visual. Nessa ordem. Você inverte isso e vai ter um painel bonito com dados errados — que é pior que feio com dados certos, porque o usuário vai tomar decisão errada com confiança.

Sobre os deletes silenciosos: todo mundo aqui falou de confirmação, log, auditoria. Certo. Mas tem um nível anterior que ninguém mencionou — **por que existe um botão de deletar leads de teste em produção?** Se o ambiente é misto (dados reais + dados de teste), você tem um problema de arquitetura que nenhuma policy de RLS resolve completamente. O fix correto de longo prazo não é só criar confirmação e log — é separar contexto. Ambiente de teste não deve contaminar base de produção. O botão de delete revelou o sintoma. A causa é que não existe separação de ambiente. E isso vai aparecer de novo, de formas diferentes, enquanto essa separação não existir.

Sobre os filtros com itens inativos: a solução técnica é simples — filtrar dinamicamente pelo período selecionado, mostrar apenas campanhas com pelo menos um evento (lead, clique, conversão) naquele intervalo. Mas o design da lógica importa: "sem dado no período" não é o mesmo que "campanha inativa". Uma campanha pausada há 6 meses pode ter dado histórico relevante se o usuário está olhando aquele período. O filtro inteligente precisa respeitar o contexto temporal, não inferir inatividade permanente. Isso parece detalhe — não é. É a diferença entre filtro que ajuda e filtro que esconde.
